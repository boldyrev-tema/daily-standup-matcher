# Сноска о прошлом дейлике («саммари для саммари») — design

## Что строим

Идея перенесена из сестринского проекта `meeting_copilot` (там — «саммари для саммари»: список тем + краткое решение по каждой, для тех, кто пропустил созвон), но реализована по-своему под то, что уже есть в этом проекте — не копия того подхода, а адаптация под уже готовую live-архитектуру `daily_standup_matcher`.

При закрытии живого дейлика (`run_second_screen.py --live`) программа собирает краткую сноску — что обсуждали по каждой узнанной задаче — и сохраняет её. При следующем запуске `--live`, если есть сохранённая сноска с прошлого раза, рядом с главным окном сразу открывается маленькое отдельное окошко с этой сноской, которое можно закрыть отдельно от главного.

Только `--live`. Реплеи (Полоса/второй экран/Колонка с кнопкой «Начать») — демо на синтетических данных, сноска по ним смысла не несёт.

## Источник данных: `meeting.lines`, не `meeting.said`

`Meeting.said`/`Meeting.ask` — живые поля для текущей на экране задачи, `mark_recognized()` затирает их при переходе на новую задачу (`meeting.py:32-42`). К моменту закрытия окна там в лучшем случае данные по последней обсуждённой задаче.

`Meeting.lines` — append-only, ничего не затирается. Каждая `Line` несёт `.task` (ключ узнанной задачи или `None`). На закрытии группируем `lines` по `.task` для всех ключей из `meeting.done` (только реально обсуждённые, в порядке узнавания).

## Генерация: переиспользуем `hints.get_hints()`, не новый LLM-проход

`get_hints(lines, task, api_key, timeout)` уже существует, уже живьём проверен (реальный Groq/OpenRouter, антигаллюцинационный промпт, fallback-цепочка из 3 моделей) и уже делает ровно то, что нужно — реплики задачи → короткие строки `said`. Вызываем его по разу на каждую задачу из `meeting.done` с её полным списком реплик.

**Важная деталь, найденная при самопроверке спеки:** `get_hints` внутри себя жёстко фильтрует по `LOOKBACK_SECONDS = 90.0` от последней реплики (`_recent_lines_text`, `hints.py:64-66`) — это правильно для live-подсказки (только недавнее важно), но для сноски по всей задаче отрежет всё, что обсуждалось раньше чем 90с до конца её обсуждения. `get_hints` получает новый опциональный параметр `lookback_seconds: float | None = LOOKBACK_SECONDS` — `None` отключает фильтр (берутся все переданные реплики как есть). Существующие вызовы (`run_second_screen.py`, тесты) не меняются — дефолт тот же. `build_recap` зовёт `get_hints(task_lines, task, api_key, lookback_seconds=None)`.

Задачи, для которых `get_hints` вернул пустой `said` (ничего содержательного или сбой LLM) — в сноску не попадают. Пустая карточка «ничего не сказано» бесполезна.

## Формат и место хранения

`recap.py`:

```python
def build_recap(meeting: Meeting, agenda: list[Task], api_key: str) -> list[dict]:
    """Для каждого key из meeting.done: собрать meeting.lines с этим .task,
    вызвать get_hints(lines, task, api_key). Пропустить задачи с пустым said.
    Вернуть [{"key": ..., "title": ..., "said": [...]}, ...] в порядке done."""

def save_recap(records: list[dict], dir: str = "recaps") -> str:
    """os.makedirs(dir, exist_ok=True), записать
    {"generated_at": ISO-строка, "tasks": records} в
    "<dir>/<generated_at как YYYY-MM-DD_HH-MM-SS>.json". Вернуть путь."""

def latest_recap(dir: str = "recaps") -> dict | None:
    """Самый свежий *.json по имени файла (сортировка по имени = по времени,
    формат имени это гарантирует). None, если папки нет или она пуста."""
```

`recaps/` — в `.gitignore`, рядом с (пока не заведённой) `transcripts/`. Репозиторий публичный, в сноске — реальные имена коллег Рината и содержание рабочих обсуждений, коммитить нельзя.

## Не блокировать закрытие окна

Сама генерация — до 6 вызовов `get_hints` по 2-4с каждый (последовательно, `get_hints` не асинхронный) — секунды, иногда десятки секунд. Синхронно в обработчике `closing` — окно виснет в точности как только что найденный и почин­енный баг с кнопкой «×» (`live_audio.py` уже показал: `window.destroy()` внутри JS-колбэка — самый частый источник такого зависания у pywebview, но тут проблема шире — сама Python-функция на closing блокирует поток pywebview, а не только сам destroy).

Решение: `window.events.closing` в `_run_live` (`run_second_screen.py`) получает ещё один обработчик — он **не** ждёт результата, а стартует **не-daemon** поток на `build_recap`+`save_recap`. pywebview закрывает окно немедленно (как сейчас), а сам процесс Python не завершается, пока не-daemon поток не допишет файл — разница в несколько секунд между «окно исчезло» и «процесс закончился», невидимая пользователю. Если `api_key`/сеть недоступны — `get_hints` уже штатно возвращает `([], None)` на любой сетевой сбой, весь дейлик просто не сохранится (не крашится).

## Окно сноски

Новое `recap.html` + создание второго `webview.create_window(...)` в `run_second_screen.py`, только когда `"--live" in sys.argv` и `recap.latest_recap()` не `None` — создаётся до `webview.start(...)`, рядом с основным окном (pywebview поддерживает несколько окон в одном GUI-цикле).

~380×500, те же тёмные токены (`rgba(19,18,23,.86)` + blur), что у трёх основных размещений — не придумываем новую палитру. Заголовок — дата/время дейлика из `generated_at`. Список задач: заголовок задачи + буллеты `said`. Кнопка «×» — та же схема с не-daemon-потоком на `window.destroy()`, что только что заведена в трёх существующих окнах (переиспользуем, не изобретаем заново).

Показ — не отслеживаем «прочитано/не прочитано». Каждый `--live`-запуск с существующим файлом в `recaps/` показывает самый свежий. Следующий дейлик перезапишет то, что видно в следующий раз, самим фактом появления нового файла.

## Тестирование

`build_recap`/`save_recap`/`latest_recap` — чистые функции над `Meeting`/файлами, юнит-тестируемые как есть (`get_hints` уже тестируется мокнутым `requests.post` в существующих тестах — тот же паттерн). Реальный живой прогон с реальным Groq — обязателен перед тем как считать фичу готовой (`hints.py`'s собственная история: мокнутые тесты не поймали баг с временн​ой меткой в цитате, поймал только живой вызов) — тот же принцип здесь.

Окно/GUI-часть — как и остальные три размещения, автотестами не покрыта, только ручная визуальная проверка.
