# Дейлик-матчер: ядро без интерфейса

## Контекст

29 авг 2026 Ринат (Tranio) прислал спеку и макеты на отдельную инициативу — живой (не постфактум) копилот на дейлике: слушает разговор в реальном времени, определяет по речи какую задачу спринта обсуждают, показывает статус/что изменилось/что не обсудили. Это не развитие `meeting_copilot` (тот работает постфактум) — отдельная ветка поверх `live_copilot_poc`.

У Рината уже есть рабочий Python-код (`match.py`, `agenda.py`, `speech_stop.py`) на его машине, проверенный на 3 реальных транскриптах Fireflies, с одним задокументированным живым багом. **У нас нет доступа к этому коду, к реальным транскриптам Fireflies или к текущему снимку спринта.** Организационный вопрос «берётся ли Артём за эту инициативу и в каком объёме» тоже ещё не решён с Ринатом.

**Первая версия этой спеки была написана по пересказу из памяти, не по первоисточнику — это нашлась и исправлена ошибка.** При повторной сверке открыл сам оригинал (техспеку и PRD через Playwright, плюс все 3 канонических MagicPath-макета — «второй экран», «колонка», «полоса», два из них вообще не были записаны в память раньше) и нашёл, что несколько вещей, которые я пометил как «не описано, беру на своё усмотрение», на самом деле прямо описаны в техспеке. Ниже спека уже исправлена по первоисточнику; расхождения отмечены явно там, где они были.

Эта итерация — реконструкция голого ядра-матчера по описанию, без ожидания доступов, чтобы понять сам механизм и накопить тестовое покрытие. Если позже появится настоящий код Рината, его будет проще сравнить с этой реализацией или подставить вместо неё, чем писать матчер с нуля впервые.

## Цель этой итерации

По тексту финализированной реплики речи + текущей повестке дня (набор задач спринта) определить, какая задача обсуждается — или явно промолчать («не уверен»), если не уверены.

Соответствует шагу 1 из порядка реализации Рината — «ядро без интерфейса».

## Не входит в эту итерацию (явно)

- UI (три слоя «Слышу/Записал/Подсказываю», любое из 3 физических размещений)
- Интеграция с `live_copilot_poc` (STT-стрим, окно суфлёра)
- Живой снимок Jira по токену (`snapshot.py`-переписка) — вместо этого локальный синтетический `sprint.json`
- Диаризация говорящих
- LLM-слой («Сказали»/«Спроси»)
- Замер задержки на реальном дейлике
- **Оптимизация задержки на длинных репликах (30-40с)** — известная дыра №2 у Рината (узнавание только по концу фразы, для длинных реплик подсказка опаздывает; его возможное решение — гонять матчер по партиалам, показывать в конспекте только по финалу). Наше ядро принимает только уже финализированные реплики целиком — эта же задержка будет присутствовать и у нас, не чиним её в этой итерации.

## Известные ограничения реконструкции (не факт, а честно обозначенный пробел)

- Список из 142 стоп-слов Рината нам не известен — строим свой список слов-паразитов/фонового шума на разумных основаниях, не копия оригинала. Механизм их использования (вес ×⅓, не полное удаление) при этом известен точно — см. `stopwords.py` ниже.
- Все тестовые данные (транскрипты, снимок спринта) — синтетика, написанная нами, честно помеченная как синтетика. Ни один реальный дейлик через это ядро не прогонялся — только просмотрено живое проигрывание чужого демо-макета (MagicPath, 29 авг), это не то же самое, что прогон нашего кода.
- **Калибровка ожиданий по recall.** Досмотренное до конца демо реально узнало только 1 задачу из 6 за весь дейлик («обсудили 1 из 6») — заметно ниже, чем можно было предположить по одному документированному багу. Наш фикс (лемматизация) должен поднять эту цифру (см. кейс 3b выше), но не факт что закроет её полностью — в демо не разбирался разбор остальных 4 неузнанных задач построчно, возможны другие причины кроме словоформ.
- Реальные макеты Рината содержат настоящие имена его коллег по Tranio и текст настоящих задач их спринта — увиденное использовано только для проверки механизма, в наш код и тестовые данные не копируется дословно: своя синтетика использует вымышленные имена и задачи.
- **Инвариант «в Jira не пишем»** (одно из 8 правил в техспеке Рината, подпись «В Jira ничего не изменено» — часть интерфейса) в этой итерации выполняется тривиально: ядро вообще не содержит кода записи в Jira, только чтение локального `sprint.json`. Явно проговариваю здесь, чтобы этот инвариант не потерялся, когда/если появится реальная интеграция с Jira.
- **Порядок работ отличается от предложенного Ринатом.** Он планировал чинить стеммер только после первого живого замера, когда станет видно, где именно теряются задачи (пункт 4 его порядка реализации, после ядра/полосы/колонки). Мы решили сразу строить с лемматизацией (`pymorphy2`), раз всё равно реконструируем механизм с нуля — нет смысла сознательно воспроизводить уже известный ему баг. Стоит сказать об этом Ринату при разговоре, чтобы он не удивился порядку.

## Архитектура

Один пайплайн без состояния между вызовами (кроме кэша IDF-весов на повестку):

```
(sprint.json, team roster) --agenda.py--> agenda (≤6 задач, отсортирована, ≤1 с тревогой)
(agenda, финализированная реплика) --match_core.py--> list[MatchResult]  # пусто = молчим
```

Расположение: новый отдельный проект `~/Desktop/daily_standup_matcher/`, свой git-репозиторий, без пуша в remote (решение о репозитории — позже, после разговора с Ринатом). Код `live_copilot_poc` и `meeting_copilot` не трогаем — та же граница, что была принята для Jira-MVP в `meeting_copilot`.

## Компоненты

### `sprint_snapshot.py`
- `Task` — dataclass: `key: str`, `title: str`, `assignee: str`, `status: str`, `updated_at: datetime`
- `load_sprint(path: str) -> list[Task]` — читает локальный JSON-фикстур. Не обращается к сети/Jira.

### `agenda.py`
- Использует поле `Task.updated_at` (см. `sprint_snapshot.py` выше) — нужно для сортировки и тревоги, обе описаны в спеке через свежесть обновления.
- `build_agenda(tasks: list[Task], team: list[str]) -> list[Task]`
  1. фильтр: `task.assignee in team`
  2. сортировка по `updated_at` убыванию (подтверждено текстом спеки — «что двигалось вчера — сверху» — и живым макетом: задачи «обновлено вчера» идут раньше задач «обновлено 2/5 дней назад»)
  3. лимит первых 6
- `pick_alarm(agenda: list[Task]) -> Task | None` — **не per-задачный флаг, а выбор ровно ОДНОЙ задачи на весь дейлик** (подтверждено живым макетом: из двух задач со статусом «Открыто повторно» в примере отмечена тревогой была только одна — самая старая). Приоритет: сперва любая задача со статусом «Открыто повторно» (если несколько — самая старая по `updated_at`), иначе задача с `≥4 дня` без обновления статуса, иначе `None`.

### `stopwords.py`
- `STOPWORDS: frozenset[str]` — русские слова-паразиты/фоновый шум (свой список, см. ограничения)
- **Механизм — скидка, не удаление**: подтверждено текстом спеки («фоновые слова речи втрое дешевле») — слово из `STOPWORDS` не выбрасывается из реплики, а участвует в подсчёте с весом `idf_weight × ⅓` вместо полного `idf_weight`.
- `stopword_discount(word: str) -> float` — возвращает `1/3`, если слово в `STOPWORDS`, иначе `1.0`; используется как множитель в `score_task` (`match_core.py`), а не как фильтр токенов.

### `lemmatize.py`
- `lemmatize(tokens: list[str]) -> list[str]` — тонкая обёртка над `pymorphy2`, лемматизация каждого токена к нормальной форме.

### `match_core.py`
- `extract_number_mentions(text: str) -> set[str]` — регекс на числовые последовательности (2+ цифры), сравнивается с числовой частью ключей задач в текущей повестке. **Подтверждено живым просмотром демо-проигрывания реального дейлика 29 авг**: спикер сказал «...с Legacy 412» — в тексте реплики уже стоят цифры «412», не слова «четыреста двенадцать». Speechmatics (STT, тот же что в `live_copilot_poc`) явно уже нормализует произнесённые числа в цифры сам — конвертер слов-в-числа не нужен.
- `compute_idf_weights(agenda: list[Task]) -> dict[str, float]` — вес слова = `1 / (число задач повестки, в заголовке которых встречается это слово-лемма)`.
- `score_task(utterance_lemmas: list[str], task: Task, idf: dict[str, float]) -> tuple[float, int]` — возвращает (сумма весов слов-лемм, общих между репликой и леммой заголовка задачи, с множителем `stopword_discount` на каждое слово; число различных пересекающихся слов). Второе число нужно для правила минимума ниже.
- `match(utterance: str, agenda: list[Task]) -> list[MatchResult]` — **список, не одна задача**: в спеке явно описан крайний случай «в одной фразе несколько задач» → показать все упомянутые, самая свежая сверху. Порядок:
  1. Явные номера в реплике, совпадающие с задачами повестки → матч на каждый, `reason="explicit_number"`, максимальная уверенность.
  2. Для задач, не найденных по номеру: `lemmatize` реплики → `score_task` по каждой оставшейся задаче повестки → задача засчитывается матчем, только если пересекающихся слов-лемм **не меньше двух** (явное правило из спеки — одного общего слова недостаточно) **и** счёт выше порога **и** с заметным отрывом от следующей по счёту задачи.
  3. Результат — список матчей (может быть пустым), отсортированный по `updated_at` задачи (самая свежая первой), как в спеке.

`MatchResult` — dataclass: `task_key: str`, `confidence: float`, `reason: str`. Пустой список `match()` = «молчим», сам по себе не заводит отдельный `None`-объект.

## Обработка ошибок

- Пустая реплика, реплика целиком из стоп-слов, или реплика с одним-единственным пересекающимся словом (правило минимума) → `match()` возвращает `[]`, без исключений.
- Пустая повестка на входе в `match()` → явная ошибка конфигурации (`ValueError`), не тихий `[]` — это баг вызывающего кода, не штатный случай неуверенности.
- Двусмысленная реплика (два кандидата с близкими счётами, недостаточный отрыв) → соответствующая задача просто не попадает в результат — правило «при сомнении молчим» из спеки Рината.

## Тестирование

Синтетический `sprint.json` (6-8 задач, минимум одна с ключом в стиле `SITE-12160`, свои вымышленные имена/заголовки — не копия реальных данных Tranio) и синтетические реплики, честно помеченные как synthetic. Обязательные кейсы:

1. Явный номер задачи в речи (в цифрах, как реально отдаёт STT — не словами) → верный матч, `reason="explicit_number"`.
2. Совпадение по ≥2 словам заголовка в точной форме → верный матч.
3. **Регрессионный кейс для бага Рината** — в речи словоформа отличается от заголовка задачи ровно так, как в его примере («сделок» в речи vs «сделка»/«сделки» в заголовке) → должен матчиться благодаря лемматизации. Живьём подтверждено (просмотр демо 29 авг), что этот же кейс дважды не сработал у Рината на реальном дейлике — это тест, доказывающий что фикс реально работает, а не просто заявлен.
3b. **Второй регрессионный кейс, найденный самостоятельно при досмотре того же демо до конца** (не из его списка дыр, но того же класса бага): демо закончилось со счётом «обсудили 1 из 6» — SITE-12170 («Функционал задач для сделок») тоже осталась нераспознанной, хотя Яков буквально сказал «готова функциональная задача для сделок». Без лемматизации точное совпадение только одно слово («сделок» — буквально совпадает), «задач»/«задача» и «функционал»/«функциональная» — разные словоформы, ниже порога в 2 слова. С pymorphy2: «задач»→«задача» и «задача»(речь)→«задача» дают ту же лемму → 2 пересекающихся леммы («задача»+«сделка»), проходит наш порог. Тест, паравфразированный (не копия текста Tranio), должен подтвердить что наш фикс закрывает и этот случай, не только документированный Ринатом.
4. **Правило минимума** — реплика пересекается ровно с ОДНИМ словом заголовка (не считая стоп-слов) → не матч, даже если это слово редкое/веское. Нужно строго ≥2.
5. **Скидка на стоп-слова, не удаление** — реплика, где заголовок совпадает по словам только вместе со стоп-словом (стоп-слово даёт вес ×⅓, не 0) → счёт ниже, чем без стоп-слова, но не обнулён; тест проверяет что множитель применяется, а не полное игнорирование.
6. **Несколько задач в одной реплике** → `match()` возвращает список из нескольких `MatchResult`, отсортированный по свежести задачи.
7. Реплика только из стоп-слов/шума → `[]`.
8. Реплика, одинаково относящаяся к двум задачам сразу (близкие счета) → ни одна не попадает в результат.
9. Несвязанный small-talk → `[]`.
10. Пустая повестка на входе → явная ошибка, не `[]`.
11. **Тревога — выбор одной задачи, не флаг у всех подряд** — повестка с двумя задачами «Открыто повторно» разной свежести → тревога только у более старой; повестка без «Открыто повторно», но с задачей ≥4 дня без обновления статуса → тревога у неё; повестка без обоих условий → `None`.
12. **Сортировка повестки** — задачи, обновлённые вчера, идут раньше обновлённых 2+ дня назад.

Плюс юнит-тесты по отдельности: `stopword_discount`, `lemmatize`, `compute_idf_weights`, `extract_number_mentions`, `build_agenda` (фильтр/сортировка/лимит), `pick_alarm`.
