# Дейлик-матчер: ядро без интерфейса

## Контекст

29 авг 2026 Ринат (Tranio) прислал спеку и макеты на отдельную инициативу — живой (не постфактум) копилот на дейлике: слушает разговор в реальном времени, определяет по речи какую задачу спринта обсуждают, показывает статус/что изменилось/что не обсудили. Это не развитие `meeting_copilot` (тот работает постфактум) — отдельная ветка поверх `live_copilot_poc`.

У Рината уже есть рабочий Python-код (`match.py`, `agenda.py`, `speech_stop.py`) на его машине, проверенный на 3 реальных транскриптах Fireflies, с одним задокументированным живым багом. **У нас нет доступа к этому коду, к реальным транскриптам Fireflies или к текущему снимку спринта** — только словесное описание механизма из техспеки, которую Ринат прислал. Организационный вопрос «берётся ли Артём за эту инициативу и в каком объёме» тоже ещё не решён с Ринатом.

Эта итерация — реконструкция голого ядра-матчера по описанию, без ожидания доступов, чтобы понять сам механизм и накопить тестовое покрытие. Если позже появится настоящий код Рината, его будет проще сравнить с этой реализацией или подставить вместо неё, чем писать матчер с нуля впервые.

## Цель этой итерации

По тексту финализированной реплики речи + текущей повестке дня (набор задач спринта) определить, какая задача обсуждается — или явно промолчать («не уверен»), если не уверены.

Соответствует шагу 1 из порядка реализации Рината — «ядро без интерфейса».

## Не входит в эту итерацию (явно)

- UI (три слоя «Слышу/Записал/Подсказываю», любое из 3 физических размещений)
- Интеграция с `live_copilot_poc` (STT-стрим, окно суфлёра)
- Живой снимок Jira по токену (`snapshot.py`-переписка) — вместо этого локальный синтетический `sprint.json`
- Диаризация говорящих
- LLM-слой («Сказали»/«Спроси»)
- Alarm-логика в повестке — в спеке упомянута, но чем именно вызывается не описано; заглушка `TODO`, уточнить у Рината
- Замер задержки на реальном дейлике
- **Оптимизация задержки на длинных репликах (30-40с)** — известная дыра №2 у Рината (узнавание только по концу фразы, для длинных реплик подсказка опаздывает; его возможное решение — гонять матчер по партиалам, показывать в конспекте только по финалу). Наше ядро принимает только уже финализированные реплики целиком — эта же задержка будет присутствовать и у нас, не чиним её в этой итерации.

## Известные ограничения реконструкции (не факт, а честно обозначенный пробел)

- Список из 142 стоп-слов Рината нам не известен — строим свой список слов-паразитов/фонового шума на разумных основаниях, не копия оригинала.
- Критерий сортировки задач внутри `agenda.py` в спеке не описан — берём сортировку по статусу задачи как разумное умолчание, легко заменить.
- Все тестовые данные (транскрипты, снимок спринта) — синтетика, написанная нами, честно помеченная как синтетика. Ни один реальный дейлик через это ядро не прогонялся.
- **Инвариант «в Jira не пишем»** (одно из 8 правил в техспеке Рината, подпись «В Jira ничего не изменено» — часть интерфейса) в этой итерации выполняется тривиально: ядро вообще не содержит кода записи в Jira, только чтение локального `sprint.json`. Явно проговариваю здесь, чтобы этот инвариант не потерялся, когда/если появится реальная интеграция с Jira.
- **Порядок работ отличается от предложенного Ринатом.** Он планировал чинить стеммер только после первого живого замера, когда станет видно, где именно теряются задачи (пункт 4 его порядка реализации, после ядра/полосы/колонки). Мы решили сразу строить с лемматизацией (`pymorphy2`), раз всё равно реконструируем механизм с нуля — нет смысла сознательно воспроизводить уже известный ему баг. Стоит сказать об этом Ринату при разговоре, чтобы он не удивился порядку.

## Архитектура

Один пайплайн без состояния между вызовами (кроме кэша IDF-весов на повестку):

```
(sprint.json, team roster) --agenda.py--> agenda (≤6 задач)
(agenda, финализированная реплика) --match_core.py--> MatchResult(task_key | None, confidence, reason)
```

Расположение: новый отдельный проект `~/Desktop/daily_standup_matcher/`, свой git-репозиторий, без пуша в remote (решение о репозитории — позже, после разговора с Ринатом). Код `live_copilot_poc` и `meeting_copilot` не трогаем — та же граница, что была принята для Jira-MVP в `meeting_copilot`.

## Компоненты

### `sprint_snapshot.py`
- `Task` — dataclass: `key: str`, `title: str`, `assignee: str`, `status: str`
- `load_sprint(path: str) -> list[Task]` — читает локальный JSON-фикстур. Не обращается к сети/Jira.

### `agenda.py`
- `build_agenda(tasks: list[Task], team: list[str]) -> list[Task]`
  1. фильтр: `task.assignee in team`
  2. сортировка по статусу (умолчание, см. ограничения выше)
  3. лимит первых 6
- Alarm: `TODO` — не реализовано в этой итерации, оставить явный комментарий-заглушку в коде с указанием что нужно уточнить у Рината.

### `stopwords.py`
- `STOPWORDS: frozenset[str]` — русские слова-паразиты/фоновый шум (свой список, см. ограничения)
- `strip_stopwords(tokens: list[str]) -> list[str]`

### `lemmatize.py`
- `lemmatize(tokens: list[str]) -> list[str]` — тонкая обёртка над `pymorphy2`, лемматизация каждого токена к нормальной форме.

### `match_core.py`
- `extract_number_mentions(text: str) -> set[str]` — регекс на числовые последовательности (2+ цифры), сравнивается с числовой частью ключей задач в текущей повестке.
- `compute_idf_weights(agenda: list[Task]) -> dict[str, float]` — вес слова = `1 / (число задач повестки, в заголовке которых встречается это слово-лемма)`.
- `score_task(utterance_lemmas: list[str], task: Task, idf: dict[str, float]) -> float` — сумма весов слов-лемм, общих между репликой и леммой заголовка задачи.
- `match(utterance: str, agenda: list[Task]) -> MatchResult`:
  1. Если найден явный номер, совпадающий с задачей повестки → немедленный матч, `reason="explicit_number"`, максимальная уверенность.
  2. Иначе: `strip_stopwords` → `lemmatize` → `score_task` по каждой задаче повестки → выбрать задачу с максимальным счётом, только если счёт выше порога **и** с заметным отрывом от второй по счёту задачи.
  3. Иначе → `MatchResult(None, reason="uncertain")`.

`MatchResult` — dataclass: `task_key: str | None`, `confidence: float`, `reason: str`.

## Обработка ошибок

- Пустая реплика или реплика целиком из стоп-слов → `MatchResult(None, reason="uncertain")` без исключений.
- Пустая повестка на входе в `match()` → явная ошибка конфигурации (`ValueError`), не тихий `None` — это баг вызывающего кода, не штатный случай неуверенности.
- Двусмысленная реплика (два кандидата с близкими счётами, недостаточный отрыв) → `MatchResult(None, reason="uncertain")` — правило «при сомнении молчим» из спеки Рината.

## Тестирование

Синтетический `sprint.json` (6-8 задач, минимум одна с ключом в стиле `SITE-12160`) и синтетические реплики, честно помеченные как synthetic. Обязательные кейсы:

1. Явный номер задачи в речи → верный матч, `reason="explicit_number"`.
2. Совпадение по словам заголовка в точной форме → верный матч.
3. **Регрессионный кейс для бага Рината** — в речи словоформа отличается от заголовка задачи ровно так, как в его примере («сделок» в речи vs «сделка»/«сделки» в заголовке) → должен матчиться благодаря лемматизации. Это тест, доказывающий что фикс реально работает, а не просто заявлен.
4. Реплика только из стоп-слов/шума → `None`.
5. Реплика, одинаково относящаяся к двум задачам сразу (близкие счета) → `None`.
6. Несвязанный small-talk → `None`.
7. Пустая повестка на входе → явная ошибка, не `None`.

Плюс юнит-тесты по отдельности: `strip_stopwords`, `lemmatize`, `compute_idf_weights`, `extract_number_mentions`, `build_agenda` (фильтр/сортировка/лимит).
